## 五、深度分析：从音乐项目到可复用产品

当前仓库已经具备三层雏形，不应推倒重来，而应"先产品化、再泛化"：

### 5.1 组件层（UI）

- 资产：`music-ui`（55 个源码文件，48 个 shadcn 基件 + dmusic 组件 + figma 回退）、`music-design-tokens`（六主题五皮肤）、`music-emotion`（小语角色）。
- 现状：行覆盖 99.45% / 分支 95.90%，但**只有代码没有说明书**。
- 产品化关键：Storybook 预览、react-docgen 自动 API、axe 可访问性、视觉回归、主题切换演示、按需引入与体积报告。

### 5.2 智能前端框架层（AI + 交互）

- 资产：`music-hooks`（`useAIAssistant` / `useAudioComposer` / `useAudioEngine` / `usePWA` / `useSwipeGesture` / `useVirtualList`）、`music-voice`（识别/合成/命令/上下文）、`music-ai`（创作工作台/MV/歌词）、`music-utils`（api/supabase/monitoring）、`music-testing`（测试运行器）。
- 现状：能力齐全，但模型调用、语音链路、网络层与业务组件耦合，难以跨场景复用。
- 产品化关键：定义四类契约——`AIProvider`（chat/lyrics/compose/stream/abort）、`VoicePipeline`（ASR→NLU→TTS）、`PromptRegistry`（版本化 Prompt）、`Guardrail`（输入输出校验）；组件只依赖契约，不直接依赖 fetch。

### 5.3 知识库层（Docs as Code）

- 资产：795 份文档、十阶段文档架构、16 包源码与测试。
- 现状：内容多但标头不统一、无站点、无检索、无法直接被 RAG 消费。
- 产品化关键：VitePress + typedoc 双站；ADR（架构决策记录）；组件目录；Prompt 库；统一 front matter 作为 RAG 元数据（时间/空间/属性/事件/关联五维标签）。

### 5.4 音乐场景的定位

音乐域包（player/lyrics/community/growth/commerce/data/audio）保留为**参考实现（Reference Vertical）**，用于验证组件层与智能框架层的真实可用性；通用能力通过契约上移，避免把音乐业务硬编码进基础库。

## 七、验收门禁（长期保留）

```bash
pnpm test:coverage        # Vitest 四项 ≥80%
pnpm test:deno:coverage   # Deno 行覆盖 ≥80%
pnpm lint                 # 0 error
pnpm typecheck            # 16/16
pnpm build                # 16/16
env -u CI pnpm e2e        # 关键旅程 100%
```

新增红线：

1. 覆盖率不得低于 80%，新增源码必须同步新增用例。
2. 新增文档必须使用 YAML front matter；CI 校验文件名与 H1 一致。
3. 新增依赖必须通过 `pnpm audit --audit-level=high`。
4. 新增公开包必须包含 README、`exports`、`publishConfig`、`files` 与示例。
5. 组件不得直接调用网络，必须经由 Provider 契约。
